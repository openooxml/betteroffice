`betteroffice-docx` can now bound its own parsing and rasterize a page. `Document::open_with_limits` takes an explicit `ParseLimits`, so a host that ingests untrusted uploads caps paragraphs, tables, XML events and nesting itself instead of inheriting the parser's defaults; a document past any cap is refused rather than silently truncated.

Under the new opt-in `raster` feature, `Document::register_font` supplies font faces for shaping and `Document::render_png` rasterizes one display-list page to deterministic PNG bytes. Registration is budgeted the same way the PPTX facade budgets it — 256 faces at 32 MiB each, plus 256 images at 32 MiB each, so 16 GiB retainable in the worst case — and exceeding any budget is a typed `Error::ResourceLimit`.

The display list is budgeted too, since it is the one input this API takes from outside. A page over 16384px per side or 16777216 pixels of area is refused before any surface is allocated, mirroring the XLSX facade. That cap lives in `docx-raster`'s own entry points rather than in the facade, so a direct consumer of the published crate is bounded by the same numbers; the facade's constants derive from the backend's.

Images are budgeted by both the pixels and the bytes they decode to: 33554432 pixels for one image and 67108864 across one page, and 268435456 bytes for one image and 536870912 across one page, charged from the declared extent and colour depth before the decoder allocates. Pixels are not memory — a 16-bit source needs twice the buffer an 8-bit one of the same extent does, and the enabled TIFF decoder goes to 32 bits per channel. A `data:` payload is bounded at 33554432 bytes, matching what a facade may register for a relationship id, and charged from its encoded length before base64 expands it. A page decodes each resolved image once however many primitives reference it, and consults that cache before decoding base64, so a repeated `data:` URL costs one decode. The cache borrows a `data:` key from the display list rather than copying it, and caps the entries and key bytes it does own.

A page also carries a work budget for what it allocates beyond its own surface. Crop masks, clip surfaces and generated paths are charged in bytes — 32 per page pixel, never under 32 MiB — because they share that unit honestly: a crop mask and a clip surface are both page-sized, and a generated path grows with a number off the display list. A wave, a dash pattern and a shape's own geometry all expand into such a path, in path space and before anything clips them, so all three are charged from the length they expand over; a length that overflows to infinity is charged as unaffordable rather than walked. Glyphs are counted rather than weighed, 1000000 across every run on the page, because a glyph costs its rasterization rather than its footprint, and the count is charged before the shaper allocates — from the uppercased text where `allCaps` is set, and from a tab leader's glyph times its repeat count.

A surface the page holds is charged its high-water mark rather than once per use. One clip surface and one crop-mask cache are alive at a time, so refilling either allocates nothing further: a page of distinct cropped images costs the cache, not one page-sized mask per reference. The crop-mask cache holds 16 masks or 8 bytes per page pixel, whichever binds, and evicts the least recently used, because a page walks its geometries in display-list order and a round robin over five of them misses every time on a cache that evicts by age of insertion. The clip surface is resized rather than grown to a running maximum, since every clipped primitive clears and blits the whole surface.

Most embedded media needs no side table: the parser resolves it to a `data:` URL against its own part's relationships, which the raster backend decodes directly. Media the parser could not resolve — an external or dangling relationship, an image outside `word/media/`, a picture watermark's bare `rId` — reaches the backend unresolved. `Document::register_image` supplies the bytes for those, keyed by owning part so a header image and a body image that share a relationship id stay distinct.

An image the backend will not draw is skipped rather than failing the page, matching the canvas backend's resolver: an unresolved reference, bytes that will not decode, and an image past a budget all leave a hole instead of taking the page down. `Document::render_png` returns that skipped count alongside the bytes, so a caller that needs a whole page rejects on it. A missing font chain still fails the page, and the asymmetry is deliberate: an image is one element and its absence is a bounded hole a caller can see and act on, while a missing chain silently empties every run in that family and reports the same success as a page that rendered.

**Behaviour change for existing consumers of `betteroffice-docx-raster`.** `ImageMap` was documented and implemented as keyed by bare relationship id. Part scoping changed that, and a map in the shape the crate shipped rendered its images as holes with no error. A body image now resolves under its bare relationship id again when the scoped key misses; a header image does not, because reaching another part's id is the cross-part lookup scoping exists to prevent, and a body relationship id that spells another part's scoped key resolves to nothing for the same reason. Two behaviours still differ from the previous release and are not restored: a missing, malformed or over-budget image is a skipped hole rather than an `Err`, and the `render_png` compatibility wrapper returns bytes alone, so it cannot report that hole. `render_page` is the form that can, and is what a caller who needs to know should move to.

The feature is off by default because the raster backend is server-side only; the default build still compiles to `wasm32-unknown-unknown`. `Document` remains `Send + Sync` with fonts registered, so it stays usable from language bindings.
